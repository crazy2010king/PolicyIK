## 二、关键实测数字

### 2.1 UDP 上报周期（L3）——`cycle` 读法定论

| `cycle` | 实测 P50 | 结论 |
|---|---|---|
| 1 | **4.998 ms**（P99 5.222 / P99.9 5.326 / max 5.342） | 读法 A（单位 = **5 ms 的倍数**）✅ |
| 5 | **24.954 ms** | 读法 A（5 × 5 = 25 ms）✅ |

⇒ 《设计文档》§二.2 写的「`cycle=5` 表示 5 ms」（读法 B）被**实测否证**；
`devices/*.yaml` 的 `udp_cycle: 1`（读法 A）正确。

### 2.2 夹爪（L9，用户重点关注）

| 项 | 实测 |
|---|---|
| 在线标志 | `status = 1`（在线） |
| 张开指令 1000 → 回读 `actpos` | **1000**（误差 **0**） |
| 闭合指令 0 → 回读 `actpos` | **12**（误差 **12**，阈值 20） |
| 末端工具供电 | 正常（夹爪在线 + 位置随指令变化 ⇒ 协议与供电均正常） |

⇒ **WHJ03 夹爪在真机上工作正常**：开合指令生效、位置回读与指令一致、
在线状态为真。设计文档 §八.3 的四坑（末端电压 / 协议 / 供电 / 0–1000 换算）
在这台设备上**均未出现**。

### 2.3 5 ms 透传抖动（L7）

30 s / 6000 拍保持位姿：P50 **0.0058 ms**、P99 **0.153 ms**、
**P99.9 0.249 ms**、max 0.317 ms；安全违规 0、传输错误 0、最终状态 `completed`。
⇒ 满足《设计文档》§六 主张 3（P99.9 < 0.5 ms）。

### 2.4 末端跟踪误差（L8）与**加速度上限**的标定

末端误差 = ‖FK(指令关节角) − FK(实测关节角)‖（MDH 正运动学，link7/法兰点）。

| 加速度上限（rad/s²） | 轨迹 | 关节误差 max | **末端误差 max** | 判定（≤ 3 mm） |
|---|---|---|---|---|
| 6.0 / 8.0（S02 自研默认） | 53 点 / 0.26 s | 1.199° | **6.51 mm** | ❌ |
| 2.0 / 2.5 | 93 点 / 0.46 s | 0.690° | **3.73 mm** | ❌ |
| **1.0 / 1.2** | 131 点 / 0.65 s | **0.472°** | **2.56 mm**（p95 2.29 / p50 1.23） | ✅ |

⇒ **「末端跟踪误差 < 3 mm」在真机上可达，但前提是把加速度上限收紧到
≈ 1.0/1.2 rad/s²**；根因是**加速段**的伺服滞后（关节滞后 1.2° ⇒ 0.3 m 力臂上 ≈ 6 mm）。
标定值已回写 `devices/rm75_b_192_168_1_18.yaml`（`accel_limits.measured: true`）。

### 2.5 电流阈值标定（G5）

真机实测暴露的问题与处理：

| 现象 | 处理 |
|---|---|
| 静态重力保持电流 J2 ≈ **-2100 mA**，而兜底阈值只有 1500 mA ⇒ **G5 会误停机** | 实测标定：`scripts/calibrate_currents.py`（静态 9 姿态 + 规划轨迹动态包络） |
| J1 加速段持续电流 ≈ **2000 mA**，起步瞬间有 **-2802 mA 单拍尖峰**（个别采样 10 A 量级） | 驱动层 G5 改为**连续 3 拍越限才停机**（`current_stop_after_ticks = 3`） |
| 只用静态包络标定 ⇒ 轨迹执行到第 10 点就被 G5 停机 | 标定口径改为「静态 ∪ 动态」分组统计 + 去抖窗口 |

标定结果（2026-11-20，`calibrated: true`）：

```
J1 3200.0 | J2 3154.5 | J3 1576.5 | J4 2005.5 | J5 600.0 | J6 681.0 | J7 600.0   (mA)
```

### 2.6 长稳（L12：100 Hz × 30 min）

`scripts/soak_test.py --hz 100 --duration-s 1800`，保持位姿
`[0.250071, 0.733667, 0.341927, -0.394183, -0.021328, 0.092363, -3.499682]` rad：

| 指标 | 实测 |
|---|---|
| 拍数 / 下发指令数 | **180000 / 180000**（一拍不丢） |
| 最终状态 | `completed`（stop_reason = completed） |
| 安全违规数 | **0** |
| 传输错误数 | **0** |
| 周期抖动 | P50 **0.023 ms**、P99 **0.222 ms**、**P99.9 0.314 ms**、max 1.007 ms |
| 命令→执行延迟 | P50 **0.104 ms**、P99 **0.182 ms**、P99.9 **0.290 ms**、max 1.72 ms |

⇒ 满足《设计文档》§七 P2「100 Hz × 30 min 无故障」与 §六 主张 3
（P99.9 < 0.5 ms）；命令→执行延迟也远低于 §六 主张 3 的 20 ms。
**8 h 长稳尚未执行**（§九）。

> ⚠️ 第一轮长稳**作废**：长稳在跑时另一个进程（轨迹执行）也去连
> `192.168.1.18:8080` ⇒ 长稳的 `rm_movej_canfd` 立刻返回 `-2`。
> 这暴露了「真机并发无互斥」的缺陷（见 §四 #15，已修）。

### 2.7 急停态（L11 的一部分）：**这台控制器不支持软件急停**

`scripts/estop_fault_test.py` 在真机上尝试用厂商接口注入急停：

| 调用 | 返回 | 含义 |
|---|---|---|
| `rm_set_arm_emergency_stop(True)` | **-4**（0.00 s 返回） | 控制器**超时拒绝** ⇒ 软件急停**不生效** |
| 急停后 `rm_set_realtime_push(enable=False)` | **阻塞 > 8 s** | 一次被拒的调用让同连接的**配置通道**不再返回 |
| 急停后 `rm_get_current_arm_state` | 0（0.01 s） | 指令/状态通道仍正常 |

⇒ 两个结论：
1. **急停必须用物理急停**（《设计文档》§五.2 第 7 闸）；
   `estop_status` 故障链在真机上**无法用软件注入**，
   只能用物理急停 + 人手确认（脚本已就绪：`scripts/estop_fault_test.py`）。
2. **厂商 ctypes 调用没有内置超时** ⇒ 我方新增 `ArmBinding.call(timeout_s=...)`
   与 `SdkCallTimeout`（守护线程 + 超时），并给**所有非实时路径**的 SDK 调用
   加了 2 s 超时（否则一次被拒调用就能挂死收尾流程 / 5 ms 执行环）。

## 四、本轮**修掉的真机缺陷**（都是阶梯跑出来的）

第一轮（只读）8 个，第二轮（运动）追加 6 个：

| # | 缺陷 | 症状 | 修复 |
|---|---|---|---|
| 1 | 线程模式常量错误 | `RM_TRIPLE_MODE_E = 3` ⇒ `Invalid thread mode`，拿不到句柄 | 改为 **2**（`device/binding.py` 唯一真相源） |
| 2 | **从不建立连接** | 只 `RoboticArm(...)`，没调 `rm_create_robot_arm` ⇒ 真机上没有链路 | 新增 `device/binding.py`（建连接 + 句柄校验 + 显式报错） |
| 3 | 调用形态错误 | 按模块级函数调用；厂商 API 其实是**实例方法** | `ArmBinding.call`：**实例方法优先** |
| 4 | 逐关节接口按整臂调用 | 使能/清错/限位签名不符 | 改为**逐轴**调用 |
| 5 | 夹爪接口签名不符 | 缺 `block` / `timeout` | 补齐 `(pos, block, timeout)` |
| 6 | 状态回读永远是 `None` | 安全闸/状态机拿不到任何真机状态 | 新增 `device/realtime.py`（主动上报 + 回调解码进 `StateSource`） |
| 7 | 顶包子模块缺失 | `Robotic_Arm.rm_robot_interface` 属性不存在 | 显式导入子模块 |
| 8 | 退出期随机段错误 | 回调对象被 GC ⇒ SDK 线程回调野指针 | 回调**进程级保活** + 不删句柄 + `os._exit` 退出 |
| 9 | **CLI 真机执行从未接上状态源** | `exec` 路径没挂 UDP ⇒ `require_state=True` 第一拍就 G7 停机 | `cli.exec` 启动主动上报、挂状态源、**等第一帧**再开跑 |
| 10 | 规划与安全层的加速度口径不一致 | 规划按 6.0/8.0 重定时、安全闸按 2.0/2.5 钳位 ⇒ 53 点轨迹被钳 **87 次** | `PlanOptions.acceleration_limits` + CLI `--accel-limits`；真机路径默认取 `devices/*.yaml` 的 `accel_limits` |
| 11 | G5 电流闸被单拍尖峰误触发 | 起步瞬间 -2802 mA ⇒ 轨迹执行中断 | 驱动层 G5 **连续 3 拍**越限才停机（纯函数安全层语义不变） |
| 12 | **起点位形不校验** | 上一次轨迹还没停稳就下发新轨迹 ⇒ 控制器**忽略新指令**，指令-反馈错位 30 mm，跟踪误差完全失真 | `cli.exec` 增加**停稳等待 + 起点一致性守卫**（默认容差 2°，不匹配直接拒绝执行） |
| 13 | `rm_get_gripper_state` 返回结构理解错 | 官方返回 `(ret, dict)`，`status` **1 = 在线**（与 UDP 帧里 `rm_plus_state` 0 = 在线相反） | 两种结构都支持，按各自文档解释 |
| 14 | `detect_local_ip` 放在 validation 层 | 设备层反向依赖验证层 | 迁到 `device/realtime.py`（设备层唯一真相源） |
| 15 | **真机并发无互斥** | 长稳在跑时另一个进程也去连 `192.168.1.18:8080` ⇒ 长稳的 `rm_movej_canfd` 立刻返回 `-2`，整轮长稳作废 | 新增 `device/hardware_lock.py`（按机械臂 IP 的 `flock` 互斥，同进程可重入），**在建连接这一步**上锁 ⇒ 所有真机入口自动受保护；被占用时报错并指出持有者 |
| 16 | **SDK 调用无超时保护** | 厂商 ctypes 调用没有内置超时：一次被控制器拒绝（`-4`）的调用之后，同连接的 `rm_set_realtime_push` **不再返回**（阻塞 > 8 s）⇒ 收尾流程被挂死 | 新增 `ArmBinding.call(timeout_s=...)` + `SdkCallTimeout`（守护线程 + 超时），所有非实时路径的 SDK 调用加 2 s 超时 |
| 17 | **软件急停在这台控制器上无效** | `rm_set_arm_emergency_stop(True)` 返回 `-4`（超时拒绝） | 如实记录：急停必须用**物理急停**；`estop_status` 故障链无法软件注入（脚本就绪，等人手） |

## 五、仍未验证 / 必须先做的三件事

1. **五类物理故障注入（L11）**：需要人手操作（拔网线、断电、制造超限位、
   夹爪夹空/物体掉落）⇒ 脚本 `scripts/fault_inject.py --hardware` 会逐步提示并等回车。
   本轮**未自动执行**（不无人值守地破坏现场设备）。
   另外：**软件急停在这台控制器上不生效**（`-4`）⇒ 急停态只能用物理急停验证。
2. **围栏参数仍是占位值**：`table_height_m = 0.75` 而实测 TCP 高度 0.754 m ⇒
   **余量只有 ~4 mm**；任何向下的小动作都会撞上 G6。必须按现场桌面高度与基座位置标定后回写。
3. **双臂（L13）**：现场只有一台臂；第二台臂到位并改 IP（`.19`）后重跑。

另外两条**待改进**（已在代码里留好接口，未在本轮实施）：
* G5 目前是**绝对阈值**；厂商未公布逐轴电流上限 ⇒ 建议追加「相对基线的电流突升」
  检测（碰撞更灵敏，且不受姿态影响）。
* **8 h 长稳**（§九）尚未执行（本轮 30 min 已通过）。
